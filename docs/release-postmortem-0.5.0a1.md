# 0.5.0a1 发布复盘（2026-09-12）

这次发布同时交付 Rust 后端、首个 alpha 通道和新的两阶段发布流水线。核心问题是发布基础设施尚未完成真实环境验收，就随产品版本一起进入首次发布；本地业务测试通过，不能证明 GitHub API、平台版本资源和签名包的发布路径已经正确。

发布执行中还有一次判断失误：在确认草稿查询语义之前直接重跑失败 job，生成了第二个空草稿，增加了恢复工作。后续应先确定远端已完成哪些写入，再决定重试。

## 故障、原因与已完成修复

| 现象 | 实际原因 | 修复与防复发证据 |
| --- | --- | --- |
| Windows 安装包构建失败 | 把 `0.5.0a1` 写进只接受数字的版本资源字段 | `e6d44d8`：数字资源用 `0.5.0`，显示版本保留完整后缀；`test_installer_numeric_version_accepts_prerelease_source` 检查版本读取和字段映射，实际 Windows CI 构建通过 |
| Windows/Linux Rust 检查失败 | macOS 专用测试的 `CancellationToken` import 未加条件编译，在其他平台成为 unused import，被 `clippy -D warnings` 拒绝 | `beddd90`：import 加 macOS 条件；三平台 Rust CI 通过。这属于跨平台检查问题，不能归因于 macOS 运行性能 |
| Apple 已接受公证，候选仍被拒绝 | 验证器把“缺少 submission ID”写成“存在 ID”，成功结果反而失败 | `d435d09`：修正布尔条件；5 个回归输入覆盖成功、拒绝、缺失或空 ID、缺失状态 |
| Actions 候选 ZIP 下载失败 | API 适配器把“响应按二进制读取”和“请求必须用 octet-stream”混为一谈，给 Actions 下载接口设置了错误 Accept | `b7ec591`：区分 Actions artifact 与 Release asset 请求；两个端点的请求头测试及真实 ZIP 摘要验证通过 |
| 文件已上传却报 `Upload not visible`，重跑生成重复草稿 | 发布器只按 tag 查询 Release，未通过有权限的 Release 列表查找草稿 | `0ecd41e`：查询回退到同 tag 草稿，多个匹配直接报错；保留原草稿和同摘要资产完成恢复 |

GitHub 官方文档将按 tag 查询定义为查询已发布 Release，并说明有 push 权限的调用方才能从列表获取草稿。API 适配层应以接口契约为依据，不能从 `gh release` 命令的行为推断 REST 查询行为。参考：[Release API](https://docs.github.com/en/rest/releases/releases#get-a-release-by-tag-name)、[Actions artifact 下载 API](https://docs.github.com/en/rest/actions/artifacts#download-an-artifact)。

另一次本地签名包测试失败来自测试方式：开发测试动态编译的临时 dylib 与 Developer ID 签名后端不属于同一签名团队，被 Library Validation 拒绝。这不构成应用签名故障。最终以真实随包 dylib 验证初始化和退出，另跑适用的签名包集成测试；没有放宽签名限制。以后须分别验证开发替身和实际签名依赖。

## 为什么测试没提前挡住

1. **变更集中，反馈太晚。** `6a0a7b3` 一次纳入 133 个文件，包含业务迁移、版本通道和发布系统。这个数字描述提交范围，不代表所有文件都存在缺陷；它让尚未真实验证的边界同时进入了发布关键路径。
2. **测试替身比真实服务更宽松。** 原来的 `FakeGitHub.release()` 直接从字典返回草稿，绕过了生产 `GitHub.release()`。因此离线“可重试”测试通过，也无法发现按 tag 查不到草稿的问题。
3. **错误假设未转成契约测试。** 数字版本字段、公证成功条件和两个下载接口的不同请求头，都是确定性的错误，本应在昂贵的签名、公证和上传前发现。
4. **把重跑当成了诊断。** 发布有持久化写入。客户端报错不等于服务器没有收到文件；重跑前没先盘点草稿、资产和 feed，扩大了恢复范围。
5. **修复 main 不会修复旧 tag 的工具。** 当前工作流从待发布 source SHA 检出发布脚本。tag 冻结后，即使 main 上修好脚本，原运行重试仍可能使用旧实现。

## 本次复盘新增的自动防线

`FakeGitHub` 现在继承生产 `GitHub`，保留真实的 `release()` 和 `optional()`，只模拟底层接口：草稿的 tag 查询返回 404，有权限的列表能找到草稿。原有发布状态测试也会经过这条真实查询路径。

新增两种上传超时场景，断言重试复用相同 Release ID、保留已有资产 ID、每个 DMG 只上传一次，且最终发布成功：

- 文件尚未被服务器接收就超时：不封存 manifest，不保存成功恢复检查点；下次只补缺失文件。
- 文件已被服务器接收，客户端却报超时：读回并核对摘要后继续，不重复上传。

验证不仅运行新测试，还在进程内临时恢复旧查询实现：两个新用例均失败；恢复当前实现后通过。这证明测试能够拦截本次历史缺陷。该实验没有修改生产文件或访问 GitHub。

本轮本地验证：发布及平台打包相关测试 90 项通过；`uv run python -m pytest -q` 全量 1013 项通过（24.53 秒）。这些结果验证了本次测试和文档补强，未进行新的线上发布或真实服务故障演练。

## 下一次发布的执行规则

1. **提前验证发布工具。** 改动发布 API、签名或恢复流程时，先提交独立变更并完成契约测试；真实服务演练必须使用明确隔离的测试目标，不能拿生产 feed 当测试数据。当前离线测试不等于完整真实服务演练。
2. **先检查，再准备候选。** 运行 Python 全量测试和相关平台 CI；使用 stable/alpha/beta 的版本契约测试，保留 Rust 三平台 `clippy -D warnings`。Windows 安装器仍需真实 Windows 构建验证，文本字段断言不能替代编译器。
3. **就绪后固定 source SHA。** 检查 Prepare Release 的来源、摘要、公证和候选封存结果，再把 tag 指向该完整 SHA。代码或发布说明变化后重新准备候选；不用移动已发布 tag 来修补版本。
4. **失败先读状态。** 记录失败 step、使用的脚本 SHA、Release ID、draft 状态、已上传资产摘要、当前 feed 和恢复快照。确定是未写入、部分写入还是读回失败后，再选择相同版本恢复路径。不得直接循环 `gh run rerun --failed`。
5. **识别旧工具。** 修复只在 main 时，不假定 `--ref main` 就能让 publisher 使用新脚本；检查 checkout 的实际 source SHA。必要的人工恢复须记录工具版本及执行步骤，继续验证原候选来源、摘要和签名，保留原 tag/DMG。
6. **以公开结果验收。** 成功回执、公开文件、签名 feed 和稳定通道隔离都验证后才宣布发布。客户端自动升级和全量包回退另有验收，不由“发布成功”推导。
