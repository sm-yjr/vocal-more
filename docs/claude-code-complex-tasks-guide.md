# Claude Code 复杂任务使用指南

## 核心思路：把 Claude Code 当作一个高级工程师来委派任务

当前问题的本质是：**任务定义不充分，导致只敢给小任务**。解决方案是学会写好 "任务 brief"。

---

## 一、任务定义的框架（最关键）

好的任务定义应该包含 **5 个要素**：

```
## 目标 (Goal)
<一段话描述最终要达到的状态，而不是步骤>

## 上下文 (Context)
<为什么需要这个改动？涉及哪些文件/模块？>

## 约束 (Constraints)
- 不要修改 <某个文件/接口>
- 保持与现有 <某个模式> 一致
- 参考 <某个文件> 的实现风格

## 验收标准 (Acceptance Criteria)
- [ ] `pytest tests/` 全部通过
- [ ] 新功能在 <某场景> 下正常工作
- [ ] 不引入新的 lint 警告

## 不做的事 (Out of Scope)
<明确排除什么，防止过度工程>
```

**验收标准是延长有效运行时间的关键** — Claude Code 会用它来自我检查，发现问题会自行修复，而不是做完就停。

## 二、利用好现有的机制

### 1. Plan Mode（规划模式）— 按 `Shift+Tab` 切换

在提出复杂任务后，先让 Claude Code 进入规划模式：

- 它会只读探索代码库，不做任何修改
- 生成逐步执行计划
- 你审核后再说 "执行" / "go ahead"

**这解决了 "担心忽略细节" 的问题** — 你可以在计划阶段就审查它的理解是否正确。

### 2. Task 列表 — 自动进度追踪

对于复杂任务，可以在提示中要求：

```
开始前先创建一个 task 列表，列出所有步骤。完成每步后标记完成。
```

这样你可以实时看到进度，知道它在做什么。

### 3. CLAUDE.md — 持久化项目上下文

`CLAUDE.md` 是编码持久项目上下文的核心工具，Claude Code 在每个会话开始时自动读取。

| 文件位置 | 作用范围 |
|---|---|
| `~/.claude/CLAUDE.md` | 全局 — 所有项目生效 |
| `<项目根>/CLAUDE.md` | 项目级 — 随 git 提交 |
| `<子目录>/CLAUDE.md` | 目录级 — 仅在该目录工作时加载 |

建议在 CLAUDE.md 中补充：

- **构建/测试命令**（这样 Claude Code 能自己验证）
- **常见陷阱**（你踩过的坑，防止它重复犯）
- **不可修改的区域**

### 4. Sub-Agent — 并行处理

对于可以并行的任务（比如给多个模块加测试），Claude Code 会自动启动子 agent 并行工作。

---

## 三、推荐的配置

以下 settings 适合复杂任务执行：

| 配置 | 推荐值 | 效果 |
|---|---|---|
| model | opus | 最强推理能力 |
| effortLevel | high | 深度思考 |
| skipDangerousModePermissionPrompt | true | 不会频繁暂停要权限 |

此外，在 `permissions.allow` 中添加常用的测试/lint 命令模式，让 Claude Code 运行验证命令时不需要手动确认。

## 四、任务定义实例对比

### 好的复杂任务定义：

```
## 目标
为 VocalMore 添加 Whisper 本地识别作为可选 ASR 后端，
用户可以在设置中切换 "云端" 和 "本地" 模式。

## 上下文
当前流程：Python 录音 → RPC 调用 Python 服务 → 云端 ASR → 返回文本
- RPC 层: src/vocal_more/rpc_handler.py
- 服务端: src/vocal_more/serve.py
- Python 应用入口: src/vocal_more/app.py

## 约束
- 不改变现有云端 ASR 路径
- RPC 协议保持向后兼容
- Python 端用 faster-whisper
- 保持当前 Python 应用的数据流与 UI 回调模式

## 验收标准
- [ ] pytest tests/ 全部通过
- [ ] 断网后本地转写正常工作
- [ ] 设置 UI 显示新选项
- [ ] 不破坏现有云端 ASR 功能

## 不做的事
- 模型下载管理（先硬编码路径）
- 本地模式的流式识别（先只做批量）
```

### 不够好的任务定义：

```
帮我加一个本地 Whisper 识别功能
```

区别在于：后者缺少约束、验收标准和范围限定，Claude Code 要么做太多（过度工程），要么做太少（遗漏关键点）。

## 五、提升运行时长的具体技巧

1. **验收标准带可执行命令** — `pytest`, `swift build`, `tsc --noEmit` 等，Claude Code 会自己跑并修复问题
2. **负面约束** — 明确说 "不要做什么"，防止它跑偏后做无用功
3. **指向参考文件** — "参考 XXX.swift 的模式"，减少它猜测的时间
4. **permissions.allow 配置更多模式** — 让常用的测试/lint 命令不需要手动确认
5. **先 Plan 后执行** — 规划阶段发现问题比执行阶段回滚代价低得多

## 六、何时拆分 vs. 保持为一个任务

### 保持为一个任务：

- 步骤之间紧密耦合（改 A 必须同时改 B 和 C）
- 需要跨多个文件积累上下文理解
- 并行化会导致合并冲突

### 拆分为多个任务：

- 步骤之间相互独立（可以安全并行）
- 每个部分可以独立验证
- 总范围超过约 50 个文件或跨多个子系统

### 推荐的混合策略：

1. 用 **Plan Mode** 先确定完整范围
2. 紧耦合的核心实现作为 **一个任务**
3. 用 **Task 列表** 追踪进度
4. 松耦合的后续工作（测试、文档）作为 **独立任务**

---

## 总结

> 给 Claude Code 的任务要像写给高级工程师的技术 brief — 说清楚目标、约束和验收标准，但不要 micromanage 每一步怎么做。
