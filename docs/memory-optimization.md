# 内存优化与原生化方向

更新：2026-09-05。目标是消除浪费、重复数据和不必要的常驻资源；100MB 是
参考值，不是通过限制功能或频繁强制 GC 来满足的硬指标。

## 本次证据和改动

本机 `/Applications/Vocal More.app` 仍为 0.4.6，PID 21731 主进程当时的
physical footprint 为 379MB。这条历史安装状态不能代表当前 0.4.10 源码。

单独运行当前源码，初始化 ASR SDK、发送线程和原生胶囊，没有连接 ASR 或
启动麦克风时，主进程约 54MB。打开设置后约 73–74MB，三次开关没有持续
增长。这是组件场景，尚未覆盖完整录音、在线润色和所属辅助进程总量。

更明确的浪费出现在历史录音播放。旧实现把整个 WAV 读入 Python，再生成
Base64 字节串、字符串和 JavaScript 调用，最后由网页解码播放。音频会跨
多个表示和进程重复存在，FLAC 还需要先完整解码到 WAV。

macOS 历史播放现在使用 AVPlayer 直接打开索引中的 WAV/FLAC 文件。设置页
只传录音 ID 和播放状态；再次点击、切换记录、离开历史页、删除正在播放的
记录、播放结束或关闭窗口都会停止并释放播放器。麦克风五秒试听和其他平台
保留原有接口。

同机、独立进程、同一份 20 分钟静音 WAV（38,400,044 bytes）结果：

| 主进程 physical footprint | 旧 Base64 播放 | 原生文件播放 |
| --- | ---: | ---: |
| 播放前 | 52MB | 53MB |
| 播放中，2 秒后 | 236MB | 62MB |
| 进程峰值 | 334MB | 62MB |
| 关闭设置，2 秒后 | 235MB | 61MB |

复现：`uv run python scripts/check_recording_playback_memory.py --backend native`
和 `--backend base64`。脚本生成临时静音文件并打开独立设置窗口，不读取用户
录音、不启动麦克风、不调用网络 API。数值来自 macOS `footprint` 的格式化
输出，主进程没有加载 ASR；不将它们当作完整应用的总占用。原生 WAV/FLAC
解码、时间推进、自然结束和播放器释放另在真实 AVFoundation 上执行通过。

设置页关闭时同步停止接收待执行 JS，清空队列并解除窗口对内容视图的引用。
这避免关闭后的大 payload 留在队列里，也避免在下次打开页面时重放旧命令。

## 下一步优先级

优先处理长录音的文件化。当前 `AudioRecorder` 持有 PCM 块，停止时 `join`
成连续字节串，存在瞬时双份数据。16kHz、单声道、16-bit 的一小时 PCM 为
115.2MB，无论使用哪种语言，整段驻留和重复拼接都会扩大内存。下一步应让
录音历史、批量识别、会议处理接受文件或流，随后把采集缓冲改成有界队列加
文件写入。实时采集回调继续只做有界交接，文件 I/O 留在普通工作线程。

设置页原生化是下一项明确的结构性优化。使用 SwiftUI 表单和列表，必要处
接 AppKit；迁移当前七个设置区域，保留配置保存、设备选择、试听、历史、
词典和模型检查的行为。先替换设置展示层，复用已有 Python 配置和服务边界，
设置窗口关闭后释放 UI。完成后 macOS 设置页可移除 WebKit 多进程开销。
实际收益以相同打开/关闭和历史列表场景测量，不提前承诺固定 MB 数。

## Rust、Go 与 Swift 的取舍

我的长期倾向是 **Swift 原生外壳 + Rust 核心**：Rust 通过 C ABI 封装网络、
状态和存储能力，可嵌入同一应用，避免仅为模块拆分再增加一个常驻服务。
Rust 无 GC 的所有权模型有利于控制缓冲生命周期，但仍需限制缓存和队列，
并不会自动解决全量音频复制。[Rust 官方介绍](https://rust-lang.org/)

**Go 核心 + Swift 外壳**也是可行方向，尤其适合优先简化网络业务开发的情况。
Go 的 GOMEMLIMIT 是软限制，只覆盖 Go runtime 管理的内存，不能把它当作
AppKit、AVFoundation、cgo 和整个应用的总上限。资源目标要留出平台框架空间，
避免为压低堆而频繁 GC。[Go GC 指南](https://go.dev/doc/gc-guide)

现有音频采集和低声 DSP 已经位于 Objective-C++ 库，具有 C ABI，先保留它。
Swift 能包装现有 C/C++ 模块，没有必要同时重写采集、增益、高通和限幅。
[Swift 官方互操作说明](https://www.swift.org/documentation/articles/wrapping-c-cpp-library-in-swift.html)

后台迁移先做一个实际 ASR 协议切片：连接、音频发送、完成、取消和重连。
用相同音频/协议事件对照 Python 的结果、首字延迟和资源增长，再在 Rust 与
Go 中定案。随后迁移配置、记录存储和业务状态，最终移除 Python host。
迁移过程避免长期同时常驻 Python、Rust、Go 三套运行时。

## 测试整理

本次删除 17 项源码字符串/实现拼写检查，约 279 行测试代码，涉及设置页、
胶囊和原生音频。保留离线打包资源、许可证、真实原生音频执行及前端交互
验证；在已有播放交互测试里补充原生停止和旧回调隔离，没有新增一组 mock
播放器单元测试。完整 Python 测试 956 项、前端 70 项通过。

后续测试以可观察行为、曾经出现的回归和关键算法为主。修改内部方法名、
目录位置或控件类型不应单独导致大量测试修改；资源检查集中到少量可复用
脚本，不为每个内部调用再添加一份断言。
